## Первые решения

**D001. Дата покупки и дата проведения дают разные месяцы учёта одной операции** (блокер · противоречие)

Покупка совершена 31 января в 23:58 по Алматы и проведена 1 февраля в 00:03. Определяется месяц, в который отнести её сумму. По правилу Ф-2 сумма относится к январю, поскольку месяц определяется датой совершения покупки. / По примеру приёмки сумма увеличивает февральский счётчик.

Разработка и тестирование не смогут однозначно определить период учёта операции; от него также зависят расчёт порога и отправка push.

**Владелец бизнес-правила учёта расходов (Product/Business owner)** — Для распределения расхода по месяцу какая дата является определяющей: дата совершения покупки или дата её проведения?

- B0014, строки 38–38 — «Месяц определяется по дате совершения покупки в Алматы.»
- B0023, строки 64–64 — «\| Покупка 31 января в 23:58 на 4 000 ₸ \| Провести 1 февраля в 00:03 по Алматы \| Февральский счётчик вырос на 4 000 ₸ \|»

**D002. После изменения порога требование отправить push не согласовано с месячным лимитом** (блокер · противоречие)

По карте в календарном месяце уже отправлен push. Затем порог изменён так, что накопленные расходы ниже нового порога; следующая покупка доводит расходы до нового порога. Ф-3 запрещает второй push по этой карте в том же календарном месяце. / Ф-4 предписывает отправить push при следующем достижении нового порога независимо от истории предыдущей настройки.

Для этого сценария нельзя выбрать единственное ожидаемое поведение уведомления и написать однозначный тест.

**Владелец бизнес-правила уведомлений (Product/Business owner)** — Если после изменения порога новое достижение происходит в месяце, когда по карте уже отправлен push, следует отправить ещё один push или соблюсти лимит одного push за месяц?

- B0015, строки 39–39 — «На карту приходится максимум один такой push за календарный месяц.»
- B0016, строки 40–40 — «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.»

**D003. Один endpoint одновременно описан как чтение и сохранение настройки** (блокер · противоречие)

Приложение вызывает GET `/alerts/saveLimit` с параметрами `cardId`, `amount` и `enabled`. Вызов только читает настройку и не изменяет её. / Вызов заменяет настройку согласно переданным параметрам.

Нельзя однозначно реализовать клиентские вызовы чтения и сохранения или проверить побочные эффекты endpoint.

**Владелец контракта REST API** — Должен ли вызов GET `/alerts/saveLimit` только читать настройку или сохранять/заменять её по переданным параметрам?

- B0042, строки 103–103 — «\| **Description** \| Сохранение порога. Функциональные требования: чтение порога \|»
- B0043, строки 104–104 — «\| **REST type** \| GET \|»
- B0048, строки 109–109 — «\| **CURL** \| `curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" --data 'cardId=demo-42&amount=50000&enabled=1'` \|»
- B0057, строки 120–120 — «4. Заменить настройку и вернуть результат сохранения.»

**D004. Отклонённая сумма представлена как ERROR в ответе, который объявлен успешным** (блокер · противоречие)

Клиент передаёт отклоняемую сумму. Для такого случая приведён ответ `ERROR` в разделе примера HTTP 200. При HTTP 200 результат классифицируется как успешный. / При отклонении суммы тело предписывает результат `ERROR`.

Клиент и тесты не смогут однозначно классифицировать отклонённое сохранение и определить ожидаемый HTTP-статус.

**Владелец контракта REST API** — Какой HTTP-статус и какое тело ответа должны возвращаться при отклонённой сумме?

- B0058, строки 121–121 — «5. При отклонении суммы вернуть прежнее состояние и результат ERROR.»
- B0069, строки 151–151 — «Если результат 200 или 201 — успешный.»
- B0077, строки 170–172 — «{"result":"ERROR","message":"Проверьте сумму"}»
- B0077, строки 170–172 — «200. Successful — Created»

**D005. Для запроса с чужой картой указаны несовместимые HTTP-статусы** (блокер · противоречие)

Владелец действительной сессии передаёт идентификатор существующей карты, принадлежащей другому клиенту. Общее правило для запрещённого доступа указывает HTTP 403. / Специальное правило для чужой карты предписывает HTTP 404.

Ожидаемый результат API для запроса с чужой картой не определён однозначно.

**Владелец контракта авторизации REST API** — Какой HTTP-статус должен возвращаться для существующей карты, принадлежащей другому клиенту: 403 или 404?

- B0078, строки 174–176 — «**403.** Ответ в случае, если на указанный ресурс доступ запрещен.»
- B0081, строки 189–190 — «Для чужой карты возвращается 404, как и для отсутствующей карты.»

### D001. Дата покупки и дата проведения дают разные месяцы учёта одной операции

**блокер · противоречие** · Правило учёта и пример приёмки должны определять один период для одной операции.

- По правилу Ф-2 сумма относится к январю, поскольку месяц определяется датой совершения покупки.
- По примеру приёмки сумма увеличивает февральский счётчик.
