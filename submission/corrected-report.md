## Первые решения

**D001. Операция API не определена однозначно: чтение или сохранение настройки**

Клиент вызывает указанный метод с новыми значениями порога и переключателя. Метод читает текущую настройку, не изменяя её. / Метод заменяет действующую настройку переданными значениями.

Нельзя однозначно реализовать метод или подготовить проверку его эффекта; заявленный GET также не снимает расхождение между чтением и сохранением.

**Владелец API / аналитик интеграции** — Какую операцию должен выполнять этот метод: читать текущую настройку или сохранять переданные значения?

- B0047, строки 103–103 — «Сохранение порога. Функциональные требования: чтение порога»
- B0062, строки 120–120 — «Заменить настройку и вернуть результат сохранения.»
- B0048, строки 104–104 — «GET»

**D002. Для ошибки суммы не согласованы HTTP-статус и результат в теле ответа**

Клиент передаёт amount вне допустимого диапазона; такой диапазон задан для этого параметра, а пример ошибки суммы помещён в раздел HTTP 200. Возвращается HTTP 200 с result=ERROR, как в примере. / Возвращается HTTP 400, поскольку значение параметра заполнено неверно.

Нельзя однозначно реализовать или проверить ответ на ошибочную сумму; клиентская обработка также может принять ответ с result=ERROR за успешный HTTP-вызов.

**Владелец API** — Какой HTTP-статус и тело ответа должны возвращаться, если amount вне допустимого диапазона?

- B0081, строки 162–163 — «**200.** Ответ в случае успешного выполнения метода.»
- B0081, строки 162–163 — «**400.** Ответ в случае, если параметры запроса заполнены неверно.»
- B0084, строки 170–172 — «{"result":"ERROR","message":"Проверьте сумму"}»

**D003. Повторное достижение после смены порога не согласовано с месячным лимитом push**

По карте уже отправлен push в текущем календарном месяце; клиент меняет порог, и расходы затем достигают нового порога. Второй push в этом календарном месяце не отправляется. / При следующем достижении нового порога отправляется push.

Нельзя однозначно реализовать повторное срабатывание или проверить месячное число уведомлений.

**Владелец продукта / аналитик бизнес-правила уведомлений** — Как должен применяться лимит в один push за календарный месяц после изменения порога?

## Дефекты отдельных требований

### D001. Операция API не определена однозначно: чтение или сохранение настройки

**блокер** · Контракт метода должен однозначно задавать выполняемую операцию и её наблюдаемый результат.

Клиент вызывает указанный метод с новыми значениями порога и переключателя.

- Метод читает текущую настройку, не изменяя её.
- Метод заменяет действующую настройку переданными значениями.

Нельзя однозначно реализовать метод или подготовить проверку его эффекта; заявленный GET также не снимает расхождение между чтением и сохранением.

### D002. Для ошибки суммы не согласованы HTTP-статус и результат в теле ответа

**блокер** · Для одного сценария контракт должен задавать единую комбинацию HTTP-статуса и результата в теле ответа.

Клиент передаёт amount вне допустимого диапазона; такой диапазон задан для этого параметра, а пример ошибки суммы помещён в раздел HTTP 200.

- Возвращается HTTP 200 с result=ERROR, как в примере.
- Возвращается HTTP 400, поскольку значение параметра заполнено неверно.

### D004. Не уточнено, какие эффекты должны сохраняться при повторной доставке события

**существенный** · Требование об идемпотентности должно определять наблюдаемые эффекты повторной обработки и способ идентификации повтора.

Событие о покупке доставлено повторно после первой обработки, которая увеличила расходы и достигла порога.

- Повтор сохраняет исходную сумму расходов и не вызывает повторного эффекта уведомления.
- Повтор сохраняет сумму расходов, но допускает повторный эффект уведомления либо трактуется иначе, если «исходный итог» относится не ко всем эффектам обработки.

### D003. Повторное достижение после смены порога не согласовано с месячным лимитом push

**блокер** · Правила частоты уведомлений и повторного срабатывания должны определять единый исход при смене порога в том же календарном месяце.

По карте уже отправлен push в текущем календарном месяце; клиент меняет порог, и расходы затем достигают нового порога.

- Второй push в этом календарном месяце не отправляется.
- При следующем достижении нового порога отправляется push.

Нельзя однозначно реализовать повторное срабатывание или проверить месячное число уведомлений.
