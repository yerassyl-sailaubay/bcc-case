## Первые решения

**D001. Лимит одного push за месяц конфликтует с повторной отправкой после изменения порога** (блокер · противоречие)

В течение одного календарного месяца расходы достигают прежнего порога и отправляется push. Затем порог меняют на более высокий, превышающий накопленные расходы; до конца того же месяца расходы достигают нового порога. Push не отправляется повторно, поскольку на эту карту уже приходился push в данном календарном месяце. / Push отправляется при достижении нового порога, поскольку накопленная сумма была ниже него.

Нельзя однозначно реализовать и протестировать отправку при повторном достижении порога после изменения настройки в том же месяце.

**Владелец продукта** — Если в календарном месяце push уже отправлялся, должен ли переход через новый порог после изменения настройки вызвать ещё один push в этом месяце?

- B0015, строки 39–39 — «На карту приходится максимум один такой push за календарный месяц.»
- B0016, строки 40–40 — «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.»

**D002. Для отклонённой суммы не согласованы HTTP-статус и результат операции** (блокер · противоречие)

Клиент передаёт сумму, которую метод отклоняет. Возвращается HTTP 200 с `result: ERROR`, как в примере, помещённом в раздел статуса 200. / Возвращается HTTP 400, если отклонённая сумма означает неверно заполненный параметр; статус 200 определён как успешное выполнение.

Разработчики и тестировщики не могут однозначно определить ожидаемый HTTP-статус и тело ответа; клиент может трактовать ошибку суммы как успешный вызов.

**Владелец API / команда backend** — Какой HTTP-статус и какое тело ответа должны возвращаться при отклонении суммы?

- B0058, строки 121–121 — «5. При отклонении суммы вернуть прежнее состояние и результат ERROR.»
- B0074, строки 162–163 — «**200.** Ответ в случае успешного выполнения метода. **400.** Ответ в случае, если параметры запроса заполнены неверно.»
- B0077, строки 170–172 — «{"result":"ERROR","message":"Проверьте сумму"}»
- B0077, строки 170–172 — «Статусы / 200. Successful — Created»

**D003. Для обращения к чужой карте указаны статусы 403 и 404** (блокер · противоречие)

Авторизованный клиент обращается к карте, принадлежащей другому клиенту. Возвращается HTTP 403: случай описан в разделе 403, а этот статус предназначен для запрета доступа. / Возвращается HTTP 404: для чужой карты прямо указан этот статус.

Реализация и тесты могут ожидать разные статусы для одного запроса; от статуса зависит обработка ошибки клиентом.

**Владелец API / команда backend** — Какой HTTP-статус должен возвращаться для запроса авторизованного клиента к чужой карте?

- B0078, строки 174–176 — «**403.** Ответ в случае, если на указанный ресурс доступ запрещен.»
- B0081, строки 189–190 — «Статусы / 403. Unsuccessful — Forbidden»
- B0081, строки 189–190 — «Для чужой карты возвращается 404, как и для отсутствующей карты.»

### D003. Для обращения к чужой карте указаны статусы 403 и 404

**блокер · противоречие** · Для одного условия доступа к ресурсу контракт должен задавать единственный HTTP-статус.

## Проверка всего набора

### D001. Лимит одного push за месяц конфликтует с повторной отправкой после изменения порога

**блокер · противоречие** · Для одного сценария, карты и календарного месяца требования должны задавать единственный ожидаемый результат отправки уведомления.

В течение одного календарного месяца расходы достигают прежнего порога и отправляется push. Затем порог меняют на более высокий, превышающий накопленные расходы; до конца того же месяца расходы достигают нового порога.

- Push не отправляется повторно, поскольку на эту карту уже приходился push в данном календарном месяце.
- Push отправляется при достижении нового порога, поскольку накопленная сумма была ниже него.

Нельзя однозначно реализовать и протестировать отправку при повторном достижении порога после изменения настройки в том же месяце.

### D002. Для отклонённой суммы не согласованы HTTP-статус и результат операции

**блокер · противоречие** · Для одного сценария контракт должен однозначно задавать HTTP-статус и тело ответа; статус успеха не должен содержать несовместимый результат ошибки.

Клиент передаёт сумму, которую метод отклоняет.

- Возвращается HTTP 200 с `result: ERROR`, как в примере, помещённом в раздел статуса 200.
- Возвращается HTTP 400, если отклонённая сумма означает неверно заполненный параметр; статус 200 определён как успешное выполнение.

Разработчики и тестировщики не могут однозначно определить ожидаемый HTTP-статус и тело ответа; клиент может трактовать ошибку суммы как успешный вызов.
